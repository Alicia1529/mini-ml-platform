# Mini ML Platform：从零动手学习计划

目标：你亲手逐步写出并运行 Milestone 1，能解释每个模块为什么存在、Ray 为什么快或慢。

已有完整实现留作参考。学习过程不要求先读完现有源码，也不把“运行完整 demo”当作掌握项目。

## 我们如何配合

- 每轮只推进一个小步骤，通常是一个函数、一个测试或一次运行。
- 我先说明当前问题、输入输出和验收条件，默认不给完整实现。
- 你写代码并在自己的终端运行，把代码、输出或报错发给我。
- 我先根据你的尝试给提示；需要示例时，只给当前步骤所需的少量代码。
- 遇到报错就停在当前步骤，一起理解和修复，不顺手扩展下一模块。
- 每步结束，你能说明结果为什么出现，再进入下一步。
- 表格是路线图，不是一次性作业；后续步骤可以根据你的理解和兴趣调整。

## 练习放在哪里

开始写代码时，在仓库内建立独立的 `learning/milestone_1/` 练习项目，使用自己的虚拟环境。
现有根目录项目和 GitHub 上的完成版保留作参考。

练习从一个普通 Python 脚本开始，按需增加文件和依赖。自己的模块由自己实现，
不导入已有的 `mini_ml_platform` 成品包。只在开始学习 Ray 时安装 Ray，
只在需要 Dashboard 时安装其可选依赖。

练习项目已建立在 `learning/milestone_1/`，现有完成版仍供参考。

## 路线图

| 步骤 | 这一步亲手完成什么 | 跑起来的验收条件 | 理解重点 |
| --- | --- | --- | --- |
| 0. 找到运行环境 | 确认终端当前目录、Python 版本和 uv 是否可用 | 能指出正在使用哪个 Python | 仓库、解释器、虚拟环境各是什么 |
| 1. 第一个脚本 | 建立练习目录、最小 pyproject.toml 和独立环境，写 hello.py | 从自己的终端打印一行文字 | 编辑代码 → 保存 → 运行的完整循环 |
| 2. 一条消息 | 写一个接收字符串、返回是否命中关键词的函数 | 手动运行安全、命中、大小写三个例子 | 先确定规则，再写实现 |
| 3. 第一个测试 | 安装 pytest，把一个手动例子变成自动测试 | 自己运行一次通过的测试，再故意改错观察失败 | 测试如何表达预期，如何读失败信息 |
| 4. 一组消息 | 先构造五条带 ID 的消息，再增加可重复的合成数据生成 | 数量、ID、固定 seed 的输出符合预期 | 输入和结果如何关联，为什么需要可复现 |
| 5. 分批 | 写 split_batches，并补边界测试 | 五条消息按二条一批得到 2、2、1；空输入和非法大小有明确行为 | batch 是什么，最后一批怎么办 |
| 6. 顺序执行 | 写处理一批和依次处理所有批次的函数 | 五条消息都有结果且顺序正确 | 消息、批次、整次运行三个层次 |
| 7. 模拟耗时 | 加入每条消息的延迟，测耗时和吞吐量 | 先用少量消息跑出第一份顺序执行测量 | 时间单位、计时边界、模拟的局限 |
| 8. 第一个 Ray Task | 安装 Ray，用独立小脚本提交一个简单任务并取得结果 | 能打印结果，并正常关闭本地 Ray | remote、ObjectRef、ray.get 各发生在何时 |
| 9. 多个任务 | 把自己的批处理函数包装成 task，提交多个批次 | 两个以上批次通过 Ray 得到完整结果 | 提交和等待的位置为什么重要 |
| 10. 验证一致性 | 比较顺序和 Ray 的完整结果，再写一个小型集成测试 | 相同输入的 ID、判断、顺序一致；最后扩到 1,000 条 | 并行完成顺序与结果顺序有什么关系 |
| 11. CLI | 逐个增加 batch size、CPU 数、延迟参数与输入检查 | 改命令参数即可运行，不再改源码常量 | 程序边界和清晰的错误信息 |
| 12. Dashboard | 安装可选依赖，启动并保持本地运行可供观察 | 在界面找到自己提交的 task 和状态 | 将代码里的提交与实际执行对应起来 |
| 13. 自己做实验 | 分开研究 CPU 数、batch size、worker 失败 | 每个实验都有预测、测量、解释和一个待解问题 | 用证据修正自己的执行模型 |

步骤 4 先用小数据理解行为，到步骤 10 再运行完整规模。
步骤 11 一次只加一个参数；步骤 13 的三个实验分三轮完成。
练习过程中逐步加入类型提示和必要的错误处理，不提前设计 SDK 或抽象层。

## 每轮使用同一个节奏

1. **当前问题**：这一小步解决什么？
2. **你的预测**：你认为输入会产生什么结果？
3. **你的实现**：先尝试写最少的代码。
4. **你的运行**：你执行命令，观察真实输出。
5. **一起复盘**：结果符合预测吗？哪里需要调整？

我给出的任务会包含目标文件、输入输出示例和运行方式；默认先提供接口或提示，
由你填写实现。你可以随时说“再小一点”“给一个提示”或“这一段请示范”。

## 三个实验的边界

- **CPU 数**：固定其他条件，依次尝试 1、4、8；分别记录执行时间和初始化时间。
- **Batch size**：固定 CPU 数，改变批大小，再比较有延迟与无延迟的运行。
- **失败**：亲手添加一次 worker 异常，追踪它在哪里出现；随后恢复并运行测试。

每次运行前先预测。本计划不提前填写结论；后续可以把结果记到现有的
`docs/learning_journal.md`。

## 完成标准与停止点

- 你能独立启动自己的顺序和 Ray 执行路径。
- 你能改 batching、并发和延迟参数，并用测试检查结果。
- 你能在 Dashboard 中定位自己提交的任务。
- 你能解释一次观察到的性能差异和一次任务失败。

本计划到 Milestone 1 为止。完成这些步骤、你准备好之后，再讨论 Actors、Jobs SDK 和 Serve。

当前进度：已写出关键词判断、分批、顺序执行和 Ray Task，并验证 1,000 条消息的结果一致；下一步模拟每条消息的处理耗时。
